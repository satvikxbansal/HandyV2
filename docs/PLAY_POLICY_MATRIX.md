# Handy Play Policy Matrix

Lane: **A — general screen-aware AI copilot**.

This is the Phase 0A policy matrix from [`HANDY_NEXT_LEVEL_PLAN.md`](../HANDY_NEXT_LEVEL_PLAN.md). It is draft Console copy for the later PLAY1 submission pass; do not paste it into [`PLAYSTORE_SUBMISSION.md`](../PLAYSTORE_SUBMISSION.md) until Phase 4 capabilities ship and PLAY1 rewrites the actual submission.

Related docs: [`SECURITY_MODEL.md`](SECURITY_MODEL.md), [`PRIVACY_MODEL.md`](PRIVACY_MODEL.md), [`ACTION_POLICY.md`](ACTION_POLICY.md), and [`Handy_Android_Build_Plan_V2_Scope.md`](../Handy_Android_Build_Plan_V2_Scope.md).

Confirmation levels match [`ACTION_POLICY.md`](ACTION_POLICY.md): `NONE`, `NORMAL`, `STRONG_HOLD`, `TYPED_CONFIRMATION`, and `BLOCKED`.

| Feature | API used | User benefit | In-app disclosure copy | Confirmation level | Risk class | Play justification verbatim for the Console |
|---|---|---|---|---|---|---|
| Floating widget and overlay chat panel | `SYSTEM_ALERT_WINDOW`, `WindowManager`, Compose overlay host | Lets the user ask Handy about the current screen without leaving the app they are using. | "Handy can show a floating widget and chat panel over other apps so you can ask about what is on screen." | `NONE` | `LOW` | "Handy uses overlay permission to show a user-controlled floating widget and chat panel. The overlay is visible, can be dismissed, and exists only so users can ask Handy about their current screen and review action confirmations." |
| Quick Settings tile, launcher, and optional Assist entry | `TileService`, launcher intent, optional Assist role or voice interaction entry point | Gives the user explicit entry points for chat, voice, or full-screen mode. | "Handy opens only when you tap the widget, app icon, tile, or enabled Assist entry." | `NONE` | `LOW` | "Handy provides explicit user-launched entry points through the launcher, Quick Settings tile, and optional Assist entry. These entry points do not run background automation." |
| Screen-text and UI-structure grounding | `AccessibilityService`, `rootInActiveWindow`, `getWindows`, `AccessibilityNodeInfo` metadata | Lets Handy explain visible UI, answer questions about controls, and ground pointer/action targets. | "When enabled, Handy can read visible screen text, UI labels, and control structure in the foreground app. Handy does not read password, OTP, card, or secure-window content." | `NONE` for explanation and pointing; action rows below govern execution | `MEDIUM` | "Handy uses AccessibilityService after prominent disclosure and user consent to read visible UI labels, roles, bounds, and window metadata in the foreground app. This is necessary for a general screen-aware AI copilot to explain the current screen, point at visible controls, and verify user-requested actions. Handy is not submitted as a disability-focused accessibility tool." |
| Accessibility marks and semantic pointer guidance | `AccessibilityNodeInfo` bounds, view id, text, content description, overlay pointer rendering | Points the user at the right visible control without requiring an action. | "Handy may point at visible controls to guide you. Pointing does not tap, type, scroll, send, pay, delete, or submit anything." | `NONE` | `LOW` | "Handy uses accessibility node metadata to identify visible controls and show a pointer overlay. Pointer guidance is advisory only and does not perform an action." |
| Screenshot or focused-window capture | `AccessibilityService.takeScreenshotOfWindow` on API 34+, `takeScreenshot` on API 30-33, MediaProjection on API 26-29 where explicitly enabled | Helps Handy answer visual questions that cannot be answered from screen text alone. | "Handy may use a screenshot for a specific request when screen text is not enough. Secure windows and blocked captures are never sent." | `NORMAL` when broader capture is needed; `NONE` for text-only turns | `HIGH` | "Handy captures screen images only for user-initiated requests that require visual context. Handy prefers text-only or focused-window capture, never sends secure-window captures, and does not store screenshots in crash logs." |
| Cloud and local AI responses | Anthropic or Gemini cloud APIs through `LlmClient`; Gemini Nano or local GenAI through `LocalGenAiClient` | Generates explanations, summaries, translations, and intent interpretation. | "Your message and the minimum needed screen context may be sent to the selected AI provider. Local AI tasks stay on device when available." | `NONE` | `MEDIUM` | "Handy sends only the user request and budgeted, redacted context needed to answer it to the selected AI provider. Local model paths are used only for supported on-device tasks." |
| Voice input and transcription | `RECORD_AUDIO`, Android `SpeechRecognizer`, optional provider-specific STT | Lets users ask questions hands-free. | "When you press and hold or start voice, Handy listens for your request and converts it to text. Handy does not listen in the background." | `NONE` after Android microphone grant | `MEDIUM` | "Handy uses microphone access only when the user starts voice input. Audio is used to transcribe the user's request and is not used for ambient listening." |
| Spoken responses | Android `TextToSpeech` or selected TTS provider | Reads Handy responses aloud when the user chooses voice output. | "Handy can speak its answer aloud when voice output is enabled." | `NONE` | `LOW` | "Handy uses text-to-speech only to read assistant responses back to the user." |
| Web search and fetched-page evidence | Network requests through the web/search tool path; typed `SourceTrust` envelopes | Answers questions that need fresh public information while treating fetched content as untrusted. | "Web pages and search results can inform answers, but web content cannot make Handy act on your phone." | `NONE` for answers; actions from fetched content are `BLOCKED` unless separately requested by the user | `MEDIUM` | "Handy may fetch public web content for user-requested answers. Fetched content is treated as untrusted evidence and cannot directly trigger device actions." |
| Tutor mode and proactive nudges | Accessibility context, local timers, optional local AI summaries | Provides slow explanations and visible guidance after explicit opt-in. | "Tutor mode can observe visible app context and offer occasional guidance. It does not click, type, scroll, or run workflows by itself." | `NONE` for nudges; action rows govern execution | `MEDIUM` | "Tutor mode is opt-in, user-visible, rate-limited, and advisory. It does not autonomously operate the device." |
| Benign visible tap in the current app | `AccessibilityNodeInfo.performAction(ACTION_CLICK)` first; `dispatchGesture` fallback only when policy allows | Performs a single visible tap the user explicitly requested. | "Handy can tap a visible control you ask for after checking the screen still matches." | `NORMAL`; future no-extra-confirm path only for clearly requested benign one-step actions if policy allows | `MEDIUM` | "Handy performs only user-requested, policy-approved taps on visible foreground controls. Each tap is grounded in a fresh accessibility snapshot, checked for confidence, and recorded in the local action audit." |
| Long-press visible semantic node | `ACTION_LONG_CLICK`; `dispatchGesture` fallback only when policy allows | Performs a single visible long-press requested by the user. | "Handy can long-press a visible control you ask for after checking the screen still matches." | `NORMAL` | `MEDIUM` | "Handy performs user-requested long-press actions only on visible, actionable foreground controls after policy approval and confirmation." |
| Scroll one viewport or explicit directional swipe | `ACTION_SCROLL_FORWARD`, `ACTION_SCROLL_BACKWARD`, or policy-approved `dispatchGesture` | Helps the user move through visible content without open-ended searching. | "Handy can scroll one page or swipe in a direction you explicitly request. It will not keep scrolling until it finds something." | `NORMAL` | `MEDIUM` | "Handy performs bounded, user-requested scroll or swipe actions only once per request unless the user asks again. It does not run hidden UI traversal or repeated retries." |
| Open notification shade or Quick Settings | Accessibility global actions where supported | Lets the user open system surfaces they explicitly requested. | "Handy can open the notification shade or Quick Settings when you ask." | `NORMAL` | `MEDIUM` | "Handy can invoke system surfaces only after an explicit user request and visible confirmation. It does not operate system settings in the background." |
| Message send, call, share, post, or navigation start | Accessibility action, Android intent, `PendingIntent`, or `RemoteInput` depending on target | Completes communication or navigation tasks only when the user confirms the exact action. | "Before sending, calling, sharing, posting, or starting navigation, Handy will show exactly what it will do and require a hold confirmation." | `STRONG_HOLD` plus fresh snapshot | `HIGH` | "Handy requires strong user confirmation before any communication, sharing, posting, calling, or navigation-start action. The action is visible, auditable, and cancelled if the screen changes." |
| Payment, purchase, delete, or submit personal data | Any action API that could trigger payment, purchase, deletion, or personal-data submission | Not shipped in beta; prevents high-impact misuse. | "Handy will not pay, purchase, delete, or submit personal data in this beta." | `BLOCKED`; later `TYPED_CONFIRMATION` only after policy review | `CRITICAL` | "Handy blocks payment, purchase, delete, and personal-data submission actions in beta. These actions are not executed through AccessibilityService." |
| Ordinary text entry | `AccessibilityNodeInfo.ACTION_SET_TEXT` with `ACTION_ARGUMENT_SET_TEXT_CHARSEQUENCE` | Fills user-approved text into a visible editable field. | "Handy can type ordinary text into a visible field after showing the exact text first. You can edit or cancel before it types." | `NORMAL` plus fresh snapshot | `HIGH` | "Handy uses ACTION_SET_TEXT only for visible editable fields after user confirmation. It does not simulate keystrokes, does not type into sensitive fields, and verifies the text-change event after execution." |
| OTP, password, card, CVV, or other sensitive field typing/reading | Accessibility text APIs are intentionally denied for these labels and secure fields | Protects credentials and high-risk secrets. | "Handy will not read or type passwords, OTPs, card numbers, CVVs, or secure-field contents." | `BLOCKED` | `CRITICAL` | "Handy refuses to read, send to AI, or type credential, OTP, card, CVV, password, or secure-field content." |
| Intent-first system tasks | Android intents for app launch, settings deep links, web search, share URL, calendar, reminder, SMS compose, navigation | Uses platform-supported user-visible flows instead of tapping through UI. | "When Android offers a safer system action, Handy opens that flow instead of tapping through screens." | `NORMAL`; `STRONG_HOLD` for cross-app send, share, call, text, or navigation start | `MEDIUM` or `HIGH` by action | "Handy prefers Android intents for system tasks because they are explicit, user-visible, and constrained by platform permission boundaries. Sensitive intents require confirmation and audit." |
| Notification summary, read, filter, group, and open source app | `NotificationListenerService`, `StatusBarNotification`, Android app intents | Summarizes recent notifications the user opted to share and opens the relevant app on request. | "If you enable notification access, Handy can summarize visible notifications and open the source app. It will not auto-triage, auto-reply, or auto-dismiss." | `NONE` for summary; `NORMAL` to open source app | `HIGH` | "Handy uses Notification Listener access only after opt-in disclosure to summarize user-visible notifications and open the source app when requested. Handy does not run ambient notification triage or background auto-reply rules." |
| Notification reply or dismiss | `Notification.Action`, `RemoteInput`, `PendingIntent.send`, notification cancel APIs where supported | Lets the user reply to or dismiss a notification with explicit confirmation. | "Handy can reply to or dismiss a notification only after showing the exact action and requiring a hold confirmation." | `STRONG_HOLD` plus audit | `HIGH` | "Handy sends notification replies or dismisses notifications only after explicit user confirmation. Each action uses the platform notification action path and is written to the local action audit." |
| Clipboard summarize, rewrite, translate, explain, or write back | `ClipboardManager`, Android 13 sensitive clip extras where supported | Helps with copied text only while Handy is visible or explicitly asked. | "Handy can help with copied text only when Handy is visible or you explicitly ask. It does not watch your clipboard in the background." | `NONE` for explicit transform; `NORMAL` when writing sensitive transformed text back | `HIGH` | "Handy uses clipboard access only for visible, user-requested clipboard assistance. It does not perform ambient clipboard surveillance, deduplicates by hash, size-caps large clips, and avoids password-like or OTP-like content." |
| Deterministic app recipes | `RecipeRegistry`, policy-gated accessibility actions, Android intents, per-step verification events | Runs bounded multi-step tasks such as Clock, Settings, Gmail, WhatsApp, Chrome, Maps, and shopping search flows without letting the LLM execute arbitrary plans. | "For supported recipes, Handy shows the plan, asks approval, executes one verified step at a time, and stops if the app or screen changes." | Plan approval plus per-step `ActionPolicyEngine` decision; sensitive steps use `STRONG_HOLD`; payment and deletion are `BLOCKED` | `HIGH` | "Handy's multi-step tasks are deterministic app recipes, not LLM-executed plans. The LLM may choose a recipe and arguments, but every step is predefined, capped at five steps, policy-checked, confirmed when sensitive, verified, and audited." |
| Hindi and Hinglish voice or shopping assistance | Android STT/TTS, locale-aware prompts, shopping-domain web/search tools, recipe rules | Makes screen-aware help usable for Hindi/Hinglish and shopping comparison tasks. | "Hindi and Hinglish help follows the same safety rules. Handy can search and compare, but it will not purchase or pay." | `NORMAL` for search/compare; `STRONG_HOLD` for navigation/send; purchases and payments are `BLOCKED` | `HIGH` | "Handy supports Hindi and Hinglish requests through the same policy engine. Shopping flows are limited to search, compare, and coupon discovery; purchase and payment actions are blocked." |
| Action audit and DiagnosticsActivity | Local rolling JSON audit file, `DataStore`, read-only diagnostics UI | Lets users and reviewers see what Handy did, why, and whether it was blocked. | "Handy keeps a local audit of actions, confirmations, failures, and policy blocks so you can review or disable behavior." | `NONE` | `LOW` | "Handy records local, redacted action audit events for transparency. Audit entries include action type, target app, confirmation state, policy result, and outcome; they do not store screenshots or raw secrets." |
